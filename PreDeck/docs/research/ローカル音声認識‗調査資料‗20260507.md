# ローカル音声認識 調査 2026-05-07

対象アプリ: PreDeck（プレデキ）新規開発版  
前提設計書: `PreDeck_最終技術選定_UIUX設計決定書(3).md`  
調査目的: 音声データをインターネットに送らず、ローカルPC内で完結する音声認識方式を選定する。

---

## 1. 結論

PreDeck をローカルPC完結で開発する場合、音声認識の第一候補は **faster-whisper** とする。

ただし、将来拡張や配布安定性を考えると、最初から `AsrEngine` 抽象化を設け、以下の複数エンジンを差し替え可能にしておくのが望ましい。

| 用途 | 推奨エンジン | 判断 |
|---|---|---|
| MVPの正式文字起こし | **faster-whisper** | 第一候補 |
| 低スペックPC・配布安定性 | **whisper.cpp** | 代替候補 |
| リアルタイム字幕・声追従 | **sherpa-onnx** | Phase 2以降 |
| 日本語精度の追加検証 | **FunASR / SenseVoice** | 比較検証候補 |
| 軽量リアルタイム補助 | **Vosk** | 補助用途 |
| ローカル完結要件では不適 | **Web Speech API** | 不採用 |
| ローカル完結要件では不適 | **OpenAI API / Google / Azure等クラウドASR** | 不採用 |

PreDeck の設計書では、Tauri 2 + React + TypeScript + Vite、Python FastAPI sidecar、SQLite + ローカルファイル保存、音声認識は faster-whisper / Web Speech API / OpenAI API が候補とされている。  
ローカル完結版では、このうち **faster-whisper を正式採用**し、**Web Speech API と OpenAI API は初期MVPのローカル音声認識候補から外す**。

---

## 2. 前提条件

### 2.1 PreDeck の技術前提

設計書上の主要構成は次の通り。

| 領域 | 採用方針 |
|---|---|
| アプリ形態 | ローカルファーストのデスクトップアプリ |
| ランタイム | Tauri 2 |
| フロントエンド | React + TypeScript + Vite |
| バックエンド | Python FastAPI sidecar |
| データ保存 | SQLite + ローカルファイル保存 |
| 初期配布 | Windows .msi |
| 音声認識 | faster-whisper / Web Speech API / OpenAI API |
| AI処理 | OpenAI API / Ollama / BYOK |

今回の要件では、音声認識とAI処理のどちらも「ローカルPC完結」を優先する。

### 2.2 ローカル完結の定義

本調査では、ローカル完結を次のように定義する。

- 録音音声を外部APIへ送信しない
- 文字起こし処理をPC内で完了する
- モデル推論をPC内で実行する
- モデルの自動ダウンロードを本番動作中に行わない
- 原稿改善や分析も、ローカルモードでは外部LLMへ送信しない
- 設定でクラウド利用を明示許可した場合のみ外部APIを使う

## 3. 候補比較

## 3.1 faster-whisper

### 概要

faster-whisper は OpenAI Whisper を CTranslate2 上で高速実行する実装である。Pythonから扱いやすく、FastAPI sidecar との相性が非常に良い。

### 評価

| 観点 | 評価 |
|---|---|
| ローカル完結 | ◎ |
| Python FastAPI sidecarとの相性 | ◎ |
| Windows配布 | ○ |
| 日本語認識 | ○〜◎ |
| 長尺音声 | ○ |
| タイムスタンプ | ◎ |
| リアルタイム性 | △ |
| 実装難易度 | ○ |

### PreDeckでの使いどころ

PreDeck のMVPでは、録音完了後に文字起こしを実行し、文字おこし確認画面へ進む構成が自然である。  
faster-whisper はこの「録音後バッチ文字起こし」に最も適している。

### 推奨設定

CPUのみの一般PCでは、まず `small` または `medium` を検証する。

```python
from faster_whisper import WhisperModel

model = WhisperModel(
    "PreDeckData/models/faster-whisper-small",
    device="cpu",
    compute_type="int8",
)

segments, info = model.transcribe(
    audio_path,
    language="ja",
    beam_size=5,
    vad_filter=True,
    vad_parameters={
        "min_silence_duration_ms": 500,
    },
    word_timestamps=True,
)
```

GPU搭載PCでは、`turbo` または `large-v3` を検証する。

```python
model = WhisperModel(
    "PreDeckData/models/faster-whisper-turbo",
    device="cuda",
    compute_type="float16",
)
```

### 注意点

faster-whisper はモデル名を指定すると Hugging Face Hub から自動ダウンロードする場合がある。  
ローカル完結版では、必ず **ローカルモデルパス指定**にする。

悪い例:

```python
WhisperModel("small")
```

良い例:

```python
WhisperModel("PreDeckData/models/faster-whisper-small")
```

## 3.2 whisper.cpp

### 概要

whisper.cpp は Whisper を C/C++ で実装した軽量・ネイティブ寄りの音声認識エンジンである。Python依存を減らしたい場合や、Windows配布の安定性を優先する場合に有力である。

### 評価

| 観点 | 評価 |
|---|---|
| ローカル完結 | ◎ |
| Windows配布 | ◎ |
| Python依存なし | ◎ |
| FastAPI sidecarとの相性 | ○ |
| 日本語認識 | ○ |
| リアルタイム性 | △〜○ |
| 実装難易度 | △ |

### PreDeckでの使いどころ

- faster-whisper の配布で詰まった場合の代替
- Python依存を減らしたい場合
- CPUのみの端末で軽量実行したい場合
- モデル量子化により配布サイズを抑えたい場合

### 実装方針

MVPでは faster-whisper を先行し、`whisper.cpp` は `AsrEngine` の別実装として後から追加する。

```text
FastAPI sidecar
  └ AsrEngine interface
      ├ FasterWhisperEngine
      └ WhisperCppEngine
```

## 3.3 sherpa-onnx

### 概要

sherpa-onnx は ONNX Runtime ベースの音声処理フレームワークで、ASR、VAD、TTS、話者識別などをローカルで扱える。ストリーミング音声認識との相性がよい。

### 評価

| 観点 | 評価 |
|---|---|
| ローカル完結 | ◎ |
| ストリーミング認識 | ◎ |
| Tauriとの相性 | ○〜◎ |
| 日本語認識 | ○ |
| 将来拡張 | ◎ |
| 実装難易度 | △ |

### PreDeckでの使いどころ

MVPの正式文字起こしではなく、Phase 2以降の以下機能に向く。

- テレプロンプターの声追従
- 録音中の簡易リアルタイム字幕
- マイクテスト
- 音声区間検出
- 圧迫ピッチモードの即時応答

### 採用判断

初期MVPでは採用しない。  
ただし、将来の「テレプロンプター声追従」を重視するなら、早い段階で技術検証だけ行う価値がある。

## 3.4 FunASR / SenseVoice

### 概要

FunASR は ASR、VAD、句読点復元、話者分離などを含む音声処理ツールキットである。SenseVoice は日本語を含む多言語対応モデルとして注目候補になる。

### 評価

| 観点 | 評価 |
|---|---|
| ローカル完結 | ◎ |
| 日本語精度 | 要検証だが有望 |
| 句読点補正 | ○ |
| FastAPI sidecarとの相性 | ○ |
| Windows配布 | △ |
| 商用利用 | 要確認 |
| 実装難易度 | △〜× |

### PreDeckでの使いどころ

- 日本語プレゼン音声で faster-whisper と比較する
- 句読点や短文分割の品質を比較する

### 注意点

## 4. 不採用候補

## 4.1 Web Speech API

Web Speech API は、ローカル完結版の音声認識には不向きである。

理由:

- ブラウザ実装によってはサーバーベースで認識される
- Windows/Tauri の WebView2/Edge 系ではクラウド音声認識に依存する可能性がある
- 音声データがPC外へ送信される可能性を排除できない
- オフライン動作を保証できない

PreDeck は Windows .msi 先行配布を想定しているため、Web Speech API をローカルASRとして扱わない。

## 4.2 OpenAI API / Google Speech / Azure Speech 等

クラウド音声認識は今回のローカル完結要件では不採用とする。

ただし、将来的にユーザーが明示的に許可する「クラウド高精度モード」として用意する余地はある。

```text
初期状態: クラウド音声認識 OFF
ローカルモード: 外部送信禁止
クラウド許可モード: ユーザーが明示的にONにした場合のみ利用
```

## 7. SQLite設計案

設計書の `sessions`、`iterations`、`transcripts`、`scripts`、`analyses` に加えて、ASR管理用テーブルを追加する。

```sql
CREATE TABLE asr_models (
  id TEXT PRIMARY KEY,
  engine TEXT NOT NULL,
  model_name TEXT NOT NULL,
  local_path TEXT NOT NULL,
  language TEXT,
  size_bytes INTEGER,
  installed_at TEXT,
  is_default INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE asr_jobs (
  id TEXT PRIMARY KEY,
  session_id TEXT NOT NULL,
  iteration_id TEXT NOT NULL,
  engine TEXT NOT NULL,
  model_id TEXT NOT NULL,
  status TEXT NOT NULL,
  progress REAL DEFAULT 0,
  error_message TEXT,
  started_at TEXT,
  finished_at TEXT
);

CREATE TABLE transcript_segments (
  id TEXT PRIMARY KEY,
  transcript_id TEXT NOT NULL,
  start_sec REAL NOT NULL,
  end_sec REAL NOT NULL,
  text TEXT NOT NULL,
  avg_logprob REAL,
  no_speech_prob REAL,
  compression_ratio REAL,
  slide_index INTEGER
);
```

## 10. Strict Local Mode

ローカル完結を保証するため、設定に `strict_local_mode` を持たせる。

```json
{
  "strict_local_mode": true,
  "allow_cloud_asr": false,
  "allow_cloud_llm": false,
  "allow_model_download": false,
  "allowed_hosts": [
    "127.0.0.1",
    "localhost"
  ]
}
```

### 禁止するもの

- Web Speech API
- OpenAI API 音声認識
- Gemini API
- Azure Speech
- Google Speech
- Hugging Face Hub からの自動モデル取得
- 外部URLへのモデル取得
- 外部LLMへの原稿改善依頼

### 許可するもの

- ローカルファイル読み書き
- SQLite
- `127.0.0.1`
- `localhost`
- Ollama などローカルLLM
- ローカルASRモデル

## 11. 文字おこし結果のデータ分離

PreDeckでは、生の文字おこし、整形済みテキスト、ユーザー原稿、AI改善原稿を分けて保存する。

```text
transcripts.raw_text
  音声認識そのままのテキスト

transcripts.normalized_text
  句読点・改行・表記ゆれを軽く整えたテキスト

scripts.user_script
  ユーザーが編集した発表原稿

scripts.ai_improved_script
  AIが改善した原稿
```

理由:

- フィラー検出には raw_text が必要
- 話速分析にはセグメントとタイムスタンプが必要
- 原稿改善には normalized_text が向く
- ユーザー編集履歴とAI改善案は分けて管理すべき

## 12. MVP実装順序

## Step 1: faster-whisper単体検証

PreDeckに組み込む前に、CLIまたは単体Pythonスクリプトで検証する。

評価音声:

- 3分プレゼン
- 5分プレゼン
- 10分プレゼン
- 日本語プレゼン
- 無音多め
- 早口
- フィラー多め
- 固有名詞多め

評価項目:

| 評価項目 | 内容 |
|---|---|
| 認識精度 | 文字誤り率、固有名詞、言い間違い |
| 処理時間 | 録音時間に対する倍率 |
| メモリ使用量 | RAM使用量 |
| GPU使用量 | VRAM使用量 |
| 無音耐性 | 長い沈黙で幻覚が出ないか |
| フィラー | 「えー」「あの」「まあ」を拾えるか |
| 句読点 | そのまま読める品質か |

## Step 2: FastAPI sidecar化

Tauriから直接ASRを呼ばず、FastAPIにジョブとして投げる。

```text
React UI
  → POST /api/asr/transcribe
  → FastAPI Background Task
  → SSEで進捗通知
  → SQLiteへ保存
  → 完了後に文字おこし確認画面へ遷移
```

## Step 3: モデル管理画面

オンボーディングまたは詳細設定に、モデル管理を入れる。

```text
文字おこし方法を選択

[推奨] ローカル高精度: faster-whisper small
[高精度] faster-whisper medium / large-v3 / turbo
[軽量] whisper.cpp
[リアルタイム] sherpa-onnx
[クラウド] 使用しない
```

## Step 4: 文字おこし確認画面

表示する情報:

- セグメント単位の文字おこし
- タイムスタンプ
- スライド番号
- フィラー候補
- 聞き取り信頼度が低い箇所
- 再認識ボタン
- モデル変更して再認識

## Step 5: 原稿改善との接続

ローカル完結版では、原稿改善も外部APIへ送らない。

| 処理 | 推奨 |
|---|---|
| 句読点補正 | ローカルLLM / ルールベース |
| フィラー検出 | ルールベース |
| 話速 WPM | ローカル計算 |
| 弱気ワード検出 | 辞書 + ルール |
| 原稿改善 | Ollama |
| 構造診断 | Ollama |
| クラウドAI | 明示許可時のみ |

## 13. 実装時の技術リスク

| リスク | 内容 | 対策 |
|---|---|---|
| モデルサイズ | medium以上は配布サイズが大きい | small同梱版とモデル別配布に分ける |
| CPU負荷 | 長尺音声で処理に時間がかかる | Background Task + SSE進捗 |
| GPU依存 | CUDA環境差で動かない | CPU int8を標準、GPUは任意 |
| 自動ダウンロード | 外部通信が発生する | ローカルパス指定を強制 |
| ライセンス | モデル同梱可否が不明 | モデル別に商用可否を確認 |
| Web Speech API | 外部送信の可能性 | ローカル版では使用禁止 |
| 原稿改善 | LLMで外部送信しがち | OllamaなどローカルLLMを既定にする |
| 配布 | Python + ML依存が重い | PyInstaller/Nuitka検証、whisper.cpp代替 |
