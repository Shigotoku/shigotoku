# プレゼン画面ウィンドウが「すぐ全画面にならない」問題 — 原因と対策

対象: FastAPI + 静的 `presenter.html` / `app.js`（Edge / Chromium 系ブラウザ想定）

---

## 現象の整理

- メインから「プレゼン画面」で `window.open` した**別ウィンドウ**は、`moveTo` / `resizeTo` 等で**作業領域いっぱいに近いサイズ**にはできることが多い。
- しかし **`Element.requestFullscreen()` による真の全画面**は、ウィンドウ表示直後には入らず、**そのウィンドウ側で実際のユーザー入力が一度入ったあと**に入ることがある。
- 親ウィンドウから子の `documentElement.requestFullscreen()` を同期的・タイマー・`BroadcastChannel` 経由で何度も試しても、原理上期待できないことが多い。

---

## 根本原因（ブラウザのセキュリティモデル）

### 1. Fullscreen API とユーザー活性化（user activation）

`requestFullscreen()` は **短時間だけ有効なユーザー活性化（transient activation）** と結び付いた API として扱われる。

- 活性化は、原則として **その操作が発生した閲覧コンテキスト（ウィンドウ／タブの文書）** に紐づく。
- メイン画面でのクリックから開いたポップアップは**別の閲覧コンテキスト**であり、**親に活性化があっても子文書には自動では渡らない**。
- そのため、**子ページのロード直後や `setTimeout` 後**に `requestFullscreen()` を呼んでも、**reject／無視**されやすい。

### 2. 親から子の DOM に対して `requestFullscreen` を呼ぶ試み

実装では親が `win.document.documentElement.requestFullscreen(...)` を呼ぶ経路があるが、**子文書側に活性化が無い**ケースでは成立しない（これが「追加の実入力が必要」に見える主因のひとつ）。

### 3. 「ほぼ最大化」と「全画面」の差

- **ウィンドウの最大化・リサイズ**と **Fullscreen API** は別レイヤー。後者は上記のユーザー要件が厳しい。
- `window.open` の feature に `fullscreen` を書いても、**現行 Chromium では期待どおりの意味にならない**ことが多い（レガシー指定）。

### 4. キーを押すと全画面になりやすい理由（実装上の注意）

`presenter.html` では、`keydown` で入力欄以外から **`wantsAutoFullscreen` 時に任意のキー押下で `requestFullscreen` を試す**処理がある。

その結果:

- ポップアップにフォーカスがある状態で **F12 や矢印など任意のキー**を押すと、**信頼できる（trusted）キーボードイベント**として子文書に活性化が付き、`requestFullscreen` が通りやすくなる。
- 「DevTools を開いたから」ではなく、**実キー入力がユーザー活性化のトリガー**になっていることが多い。

### 5. プログラムからキーやクリックを「疑似発火」しても無理な理由

`dispatchEvent` で発火した `KeyboardEvent` / `MouseEvent` は **`isTrusted === false`** の合成イベントであり、**Fullscreen のようなジェスチャー必須 API の要件を満たさない**。  
「keydown をコードで流せば同じ」とはならない。

---

## 静的キャッシュ（304）について

`presenter.html` が `304 Not Modified` になることは、**スクリプトの新旧ズレ**の原因になりうる。  
Fullscreen のユーザー要件とは**別問題**。キャッシュバスト用クエリ（例: `t=`）やサーバ側の `Cache-Control` 設計は、デバッグ・更新時の再現性のために検討する。

---

## 対策案（優先度の目安）

### A. プロダクト方針として「初回だけ実入力」を許容する（コスト低・ブラウザのみ）

- ポップアップ側に **「このウィンドウを一度クリック／F キーで全画面」** などの短い説明 UI を出す。
- **任意キーで全画面を試す**現在の `keydown` 挙動は、誤爆（意図しないキーで全画面になる）の可能性があるため、**`F` やスペースのみに限定する**などへの整理も検討余地あり。

### B. 同一文書で副モニターに Fullscreen（純 Web の別ルート）

- メインでボタンが押された**同一タブの文書**なら、そのクリックの活性化で `requestFullscreen({ screen: … })` が通る**可能性**がある（API・権限・環境依存）。
- **トレードオフ**: 全画面になるのは**そのタブ全体**（メイン UI ごと副モニターへ）。別ウィンドウ分離とは設計が変わる。

### C. Tauri / Electron などネイティブシェル（クリック一回で安定させたい場合）

- OS のウィンドウ API で **指定ディスプレイへのウィンドウ作成・最大化・フルスクリーン**が可能。
- **見た目の HTML/CSS は流用しやすい**が、ウィンドウ制御のため **最小限のブリッジコード（環境分岐）はほぼ必須**。「ソース一行も変えず」は現実的ではない。

## 検証のヒント

1. ポップアップを開いた直後、**マウスで触らず**フォーカスだけポップアップにある状態で **実キー**を 1 回押す → 全画面になりやすい（trusted 入力）。
2. Console で `dispatchEvent(new KeyboardEvent('keydown', { key: 'F', bubbles: true }))` のみ実行 → 合成イベントのため **全画面にならない**ことが期待どおり。
3. フォーカスがメインにある状態でキーを押す → イベントが子に届かず **子は全画面にならない**。

---

## まとめ

| ゴール | ブラウザのみ | 現実的な手段 |
|--------|----------------|----------------|
| ポップアップを **クリック無しで確実に** Fullscreen | ほぼ不可 | ネイティブアプリ化など |
| **ほぼ最大化**まで自動 | 可能になりやすい | 既存の `moveTo` / `resizeTo` を継続 |
| **初回の実入力 1 回**なら Fullscreen | 可能 | 説明 UI + キー／クリック誘導 |
