## 1. 目的

PreDeck は現在、2つの実装系統が並存している。本書は次を目的とする。

- 両系統の関係を明文化し、混乱を防ぐ
- 当面の運用方針（どちらをどう更新するか）を整理する
- 最終的な ver2.0 一本化までの段階的な移行ロードマップ案を示す
- 未決事項を抽出し、ユーザー（意思決定者）へ提示する

本書の方針確定後、各タスクは [TODO_未実装機能リスト.md](TODO_未実装機能リスト.md) と [implementation_plan.md](dev-notes/implementation_plan.md) に転記して実装を進める。

## 2. 背景

| 時期 | 出来事 |
|---|---|
| 2026年2月以前 | 前任者がレガシー版（FastAPI + ブラウザ）を実装。Ver6.0 要件定義書で機能が確定 |
| 2026-02 | Ver6.0 完全統合版が完成。レガシー版は本要件をベースに実装済 |
| 2026-03-11 | 引継ぎ。`start.bat` の埋め込みPython化、前任者データの退避を実施 |
| 2026-05-07 | ローカルASR/LLM/UIUX の技術調査を実施（4ファイル） |
| 2026-05-08 | Ver7.0 要件定義書・AI開発指示書・設計判断記録 を確定。`プレデキ_ver2.0/` で Tauri + sidecar 構成の新MVP を着手。Phase 0/1/2 のコード完成 |
| 2026-05-14 | `docs_new/` の内容を `docs/` に統合。Ver7.0 が正本となる |

Ver6.0 → Ver7.0 で起きた主な変更：

- **配布形態**: ブラウザ起動 → Windows `.msi`（デスクトップ）
- **アーキテクチャ**: FastAPI 単体 → Tauri 2 (Rust) + React + Python sidecar
- **既定モード**: クラウド許可可 → **Strict Local Mode（既定ON）**
- **データモデル**: JSON ファイル + 部分DB → SQLite + ローカルファイル（厳密にスキーマ分離）
- **ASR/LLM**: 直叩き → 抽象化レイヤ＋Mock＋実エンジン差替え可
- **ライセンス**: 暗黙的 → `THIRD_PARTY_NOTICES.md` + `licenses/` + アプリ内画面の必須化

これらの差分により、レガシー版を Ver7.0 準拠に改修するコストは **ほぼ作り直しに近い**。そのため別ディレクトリ `プレデキ_ver2.0/` で新規実装が進んでいる。

## 6. 移行戦略の選択肢

レガシー版から ver2.0 への最終的な切替には3つの戦略が考えられる。

### Option A: ビッグバン切替（一回で全部置き換える）
- **手順**: ver2.0 が完全にレガシー版を機能カバーするまで開発 → リリース日に切替
- **長所**: ユーザー側の混乱が少ない / 並行運用コストなし
- **短所**: ver2.0 完成までレガシー版にエネルギーを取られる / 完成まで長期間
- **適用条件**: 単一ユーザー（社内利用）であり、切替日を任意に決められる場合

### Option B: フィーチャーパリティ段階移行（推奨候補）
- **手順**: ver2.0 でレガシー版主要機能を順次再実装 → 機能パリティ到達時に既定をver2.0に切替 → レガシー版を保守モードへ
- **長所**: ver2.0 を継続的に検証できる / リスク分散 / レガシー版は安全性改修のみで済む
- **短所**: 並行運用期間が長め（3〜6ヶ月想定）
- **適用条件**: 開発リソースが限られる小規模チーム

### Option C: モジュール単位切替（リスク最小化）
- **手順**: レガシー版の機能のうち、ver2.0 で再実装済の機能から順次「ver2.0 を呼び出す」形に置き換え（バックエンドだけ ver2.0 sidecar を流用、UI はレガシーUI など）
- **長所**: ユーザー体験の連続性 / 各機能で個別にロールバック可能
- **短所**: 両者の通信レイヤを作る追加コスト / 中間状態が複雑
- **適用条件**: 既存ユーザーが多く、変更を最小化したい場合

**現時点の推奨**: **Option B（フィーチャーパリティ段階移行）**

理由：
1. ユーザー（社内開発・利用）が主用途のため切替日の自由度が高い
2. ver2.0 がアーキテクチャ刷新で**作り直しに近い**ため、両者を低レベルで結合するコスト（Option C）が割に合わない
3. ユーザー指示「レガシー版も並行更新」とも整合する

## 8. 既存セッションデータの取り扱い

レガシー版のセッション・録音・原稿データは `sessions/` `recordings/` `uploads/` 配下にあるが、現状は空（前任者データは `data_archive/` に退避済）。

切替時に新規ユーザーのデータが既に蓄積されている場合は、移行スクリプトが必要：

- レガシー版の JSON セッションファイル → ver2.0 SQLite（`sessions` / `iterations` / `transcripts` / `scripts` テーブル）への変換
- 録音WebMファイル → `PreDeckData/recordings/{session_id}/{iteration_id}.webm` へ再配置
- スライド画像 → `PreDeckData/slides/{session_id}/` へ再配置

実装優先度は **データ蓄積量を見て判断**。当面は新規利用前提でよい。
