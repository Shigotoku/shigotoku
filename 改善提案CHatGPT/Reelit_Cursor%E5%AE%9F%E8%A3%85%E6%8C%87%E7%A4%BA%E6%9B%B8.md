# Cursorへの実装指示（Reelit）
添付の Reelit_開発仕様書.md を読み、既存Deckitリポジトリを基準に実装せよ。あなたは既存本番SaaSの保守責任も持つシニアエンジニアとして行動する。

## 最重要ルール
既存Deckitを壊さない。既存資産を複製して二重管理しない。Google Driveを正本とし、Workspace Studio内のGeminiを優先する。未確認のAPIを捏造しない。外部有料AIへの無断切替、本番デプロイ、破壊的DB移行、権限拡大、既存顧客データ移動は禁止。秘密値を表示しない。ユーザーの未コミット変更を上書きしない。

## 最初の作業
1. git status、構成、README、package manifests、認証、DB、Drive/Slides、Studio、課金、GCP設定、テストを読み取り専用で調査。環境変数は名前のみ確認。
2. docs/reelit/discovery.md を作成し、現行実装の根拠ファイルと行、再利用できる機能、未実装機能、技術的負債、権限、影響範囲を記録。
3. 既存のDriveフォルダ/ブランド正本/組織ID/認証をどのように共用するか、共通パッケージ案と共通API案を比較。ADRに採用理由、代替案、移行・ロールバックを記載。
4. Studioの実際の連携方法を確認。利用プラン、管理者設定、Geminiの入出力、外部通信、実行制限を公式ドキュメントとテスト環境で確認し、未確認を明示。Studioが使えない場合も手動入力で動く設計。
5. 変更予定ファイル、依存追加、GCP追加資源、概算費用、テスト計画、ユーザーが判断すべき事項を提示。既存本番への影響がある変更は承認を待つ。

## 実装順序
- P0: 独立PoC。既存ブランドを模したテスト用資産のみで縦型25秒MP4を生成。Slides背景書出し＋動的レイヤー、縦書き、タイプライター、写真3枚、CTA、BGM。出力のffprobe結果、実測時間、メモリ、費用推定を報告。Remotionライセンスを確認。実患者データは使わない。
- P1: 共通認証・ブランド・素材アダプターを実装。既存DeckitのAPI/DB契約を維持。追加変更は後方互換にし、必要ならfeature flagを使用。マイグレーションはステージングで試験。
- P2: テンプレートmanifestのschema、登録時バリデーション、バージョン管理、プレビュー、編集、非同期ジョブ、Drive出力を実装。仕様書の4テンプレートを用意。
- P3: Studio用認証済みジョブ受付と台本schema。手動ルートも維持。Studio側の設定手順を画面単位で文書化。同期呼び出しに長時間レンダーを含めない。
- P4: 承認・監査・バッチ制作・利用量・エラー回復。徳永クリニック用テスト環境で10本試験。承認前は投稿しない。
- P5: 外販向け課金、OAuth審査対応、テナント分離、運用監視、BuzzIt下書き連携。実APIがない場合はエクスポートのみ実装し、架空の成功を返さない。

## 実装成果物
コード、schema/OpenAPI、テスト、テンプレート例、Docker設定、環境変数一覧（値なし）、ステージングデプロイ手順、Studio設定手順、運用・障害復旧手順、ADR、既存Deckit回帰結果、費用実測表。docs/reelit/ にまとめる。
各段階で実行したコマンド、結果、変更ファイル、未解決事項、次の作業を報告。テスト未実行を成功扱いしない。モックと実連携を明確に区別。失敗時は原因を調査してから修正し、同じエラーの無制限再試行をしない。

## 完了判定
仕様書の受入条件をチェックリスト化。既存Deckit回帰、テナント越境拒否、Drive権限失効、JSON不正、文字あふれ、写真欠損、レンダー失敗、二重依頼、キャンセル、アップロード失敗、承認後変更、10本バッチを試験。未達は理由と修正案を記載。

まずはP0の調査と安全なPoCまで進め、既存構成に合わせた具体的な実装計画を報告せよ。実際の本番反映はユーザーの承認後とする。
