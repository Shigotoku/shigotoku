# WrapIt(ラップイット)設計メモ — DeckIt の動画版

- 状態: 構想・設計(未実装)。2026-11-27。名称は WrapIt に決定(商標は未確認。ADR-0003)。
- 旧仮称 Reelit は既存サービス(reelit.ai 等)と衝突するため使用しない。
- 位置づけ: 「資料、できた。」の DeckIt に対する「**ショート動画、できた。**」。ブランド・スタイルを守ったまま、短尺縦動画(Instagram リール / TikTok / YouTube Shorts)を量産する。
- 前提: 既存製品は変更しない。wrapit は独立した新製品として追加する(ADR-0001, ADR-0002)。
- 注意: 競合の最新価格・各社の最新仕様・ライセンス条件は**未検証**。「要確認」は着手前に必ず公式資料で確認する。

---

## 1. 何を解決するか(ユーザー価値)

| 課題 | wrapit の答え |
|------|---------------|
| 動画制作は時間がかかり、毎回デザインがばらつく | ブランド(ロゴ・色・フォント・口調)を固定したテンプレートで量産 |
| AI 動画は「AIっぽい」「事実が不正確」 | 実写・実素材+文字演出が中心。事実は承認済み情報だけ使う |
| 中小事業者・クリニックは SNS 運用の人手がない | テーマを入れる → 台本 → プレビュー → 承認 → 書き出し |
| 業種規制(医療広告等) | 台本・字幕を既存の医療広告チェッカーで検査(§7) |

**ターゲット(初期)**: 実在の写真・店舗・スタッフ素材を持つ小規模事業者(クリニック、サロン、士業、採用広報)。BuzzIt の顧客層と重なるため、販路も共有しやすい。

**競合の整理(要確認・価格は未調査)**: Canva / CapCut 等の汎用エディタ、Vrew・Lumen5 等の自動動画化、Creatomate・Shotstack・Remotion 等の動画 API。
→ 差別化は「汎用性」ではなく **ブランド一貫性・日本語タイポグラフィ・承認フロー・業種ルール・Drive/既存素材との連携**に置く。

## 2. 名前

- **決定: WrapIt(ラップイット)**。詳細な経緯は [ADR-0003](../adr/0003-product-name-wrapit.md)。
- 由来: ① 映画の "It's a wrap!"(撮影完了=「できた」)。② 日本で通じる「ラッピング(広告)」=会社のブランドで包む。→ 「会社の決まりで包んで、動画を完成させる」。DeckIt の「資料、できた。」に対し、**「動画、仕上がった。」**。
- 英語サブ案: Your Brand. Your Rules. Wrapped.
- 懸念: ラップ(食品用・音楽)との混同、映画用語としての日本での知名度の低さ。
- **公開前に必須**: J-PlatPat(第9・35・41・42類、称呼「ラップイット」)と WIPO Global Brand Database の確認、弁理士への相談。
- 名称は `deploy/build.config.mjs` の定数・フォルダ名・Firebase プロジェクト名に集約し、万一の変更はそこだけで済むようにする(名称を散在させない)。
- 第二候補: CrankIt(クランキット)。第三候補: RollIt。

## 3. 製品スコープ

### MVP に含める
1. ブランド設定(ロゴ、カラー、フォント、口調、禁止表現、既定の CTA)
2. 素材ライブラリ(写真・短い動画クリップ。許諾ステータス付き)
3. テンプレート 3 種(採用 / サービス紹介 / お知らせ)。縦 9:16、15〜30 秒
4. 台本生成(AI)または手入力 → **スロット(見出し/本文/CTA)に流し込み**
5. プレビュー(低解像度の即時)→ 書き出し(MP4 1080×1920、サムネイル)
6. 承認フロー(制作者 → 承認者)と履歴
7. 書き出しファイルのダウンロード/保存

### MVP に含めない(明確に後回し)
- 自由形式のタイムラインエディタ(CapCut 化しない)
- 生成 AI による実写風動画・音声クローン
- Google Slides をテンプレートとして描画(§4.2 参照)
- 自動投稿(BuzzIt 連携は **下書き/書き出しまで**。承認なし公開は禁止)
- 多言語、ナレーション、アバター

## 4. 重要な設計判断

### 4.1 配置・基盤(既存と同じ型に載せる)

| 項目 | 方針 | 根拠 |
|------|------|------|
| フォルダ | `wrapit/`(`landing-page/` `app/` `api/` `render/`) | 他製品と同じ分離 |
| Firebase | 専用 `shigotoku-wrapit-prod`(Auth/Firestore/Storage) | ADR-0001 |
| フロント | React + Vite(多数派)または Next.js(DeckIt と同じ) | 要決定。DeckIt と**ブランド/スタイル資産を共有する**なら Next.js、独立性重視なら Vite。推奨: **Vite**(エディタ UI が中心で SSR 不要。ビルド/デプロイが他製品と同じ) |
| API | Cloud Functions(受付・認可)+ **Cloud Run Jobs(レンダリング)** | レンダーは長時間・高メモリで Functions に不向き |
| ジョブ | Firestore に job ドキュメント → Cloud Tasks/Pub/Sub で Job 起動 | 受付と実行の分離、再試行・冪等 |

### 4.2 テンプレート方式 — 「Slides 依存」を避ける

外部提案は「テンプレ=Google Slides+manifest」だったが、**MVP は自前の JSON テンプレート(スキーマ)を推奨**する。

| 観点 | Slides をテンプレに | 自前 JSON テンプレ(推奨) |
|------|--------------------|---------------------------|
| 描画の再現性 | Slides の縦書き・回転・アニメを API で完全取得できない | こちらが仕様を決める |
| Google 依存 | 高い(Workspace 必須になりやすい) | なし |
| 編集 UX | Slides 上で編集できる | アプリ内ビジュアル編集(要開発) |
| MVP 速度 | PoC 検証が重い | 速い |

- テンプレ = `Template { id, version, aspect, fps, scenes[], slots[], theme }`。公開版は不変、変更は新バージョン。
- スロット制約: `type(text/image/video)`, `maxChars`, `maxLines`, `fitPolicy`。**時間・座標はテンプレートが決め、AI に決めさせない**。
- 将来: DeckIt のスライド → wrapit のシーンへ**変換インポート**(ブランド/文面の再利用)を別フェーズで検討。

### 4.3 レンダリング方式 — PoC で比較して決める(結論を先に出さない)

| 案 | 長所 | 懸念 |
|----|------|------|
| A. **Remotion**(React で動画)+ Cloud Run Jobs | React/TS で実装でき、日本語組版・アニメが書きやすい。プレビューと出力を同じコンポーネントで共有 | **ライセンス(2026-11-27 公式確認)**: 組織全体で3人以下なら無料(商用・SaaS・自動化も可)。4人以上は Company License が必要で、自動レンダリングは 1 レンダー $0.01(最小 $100/月)。人数の数え方は R0 で確認([詳細](./R0-LICENSE-AND-POC-PLAN.md)) |
| B. Revideo / Motion Canvas 系(OSS) | ライセンスが緩い傾向(要確認)。コード駆動 | 成熟度・日本語組版・保守性を PoC で確認 |
| C. FFmpeg + 事前レンダー済みテキストレイヤー(Skia/Canvas) | 依存が軽く原価が低い。完全に自制御 | タイポグラフィ・アニメを自前実装(工数大) |
| D. ブラウザ内レンダー(WebCodecs 等) | **サーバー原価ほぼゼロ**。待ち時間なし | 端末差・長尺・安定性。モバイル対応が課題 |

**PoC の判定基準**(同じ 25 秒・1080×1920・30fps の採用動画を作る):
1. 日本語(縦書き・禁則・段階表示)の品質
2. 生成時間(p95)とメモリ
3. **1 本あたりの原価(Cloud Run の CPU 秒・メモリ秒)**
4. ライセンスの商用可否
5. プレビューと出力の一致(同一コンポジションか)

推奨の進め方: **A と D を最初に PoC**(A=品質、D=原価)。ライセンスで A が不可なら B/C。

### 4.4 入出力とストレージ

- **保存先は Google Drive を標準**とする(DeckIt と同じ形)。選択肢は2つ: ①WrapIt 専用フォルダを自動作成 ②ユーザー/組織が指定した共有フォルダ(チームの共有ドライブ等)。設定画面で切替(`/api/google/drive/folder`、型は `packages/domain/drive-folder.ts`)。
- **OAuth スコープは `drive.file`**(最小権限)。このスコープではアプリが作成した/ユーザーが **Google Picker で選択した**ファイルしか触れない。したがって共有フォルダ指定の本番実装は URL 貼り付けではなく **Picker 選択**が必須(現状の URL 入力は暫定・モック用)。
- 出力動画は指定フォルダの `WrapIt/<プロジェクト名>/` 配下に保存。レンダリング中の一時ファイルは自社管理の Cloud Storage に置き、完了後に Drive へ書き出す。
- Google 非利用のユーザー向けに Firebase Storage 保管を代替として残す余地はあるが、MVP では作らない。ストレージ参照は `DriveProvider`/`StorageAdapter`(ADR-0002)で包んでおく。
- 一時ファイルは暗号化・期限付き(目標 24 時間以内に削除、失敗時もライフサイクルで回収)。素材の永続的な二重保存は避ける(ユーザーのダウンロードを正とする)。

### 4.5 AI(台本)

- 既存の Gemini 利用(BuzzIt の AI 台本・Repurpose)の**パターンを踏襲**。キーは Secret Manager(ブラウザに出さない)。
- 入力は最小限(ブランド情報・テンプレのスロット制約・承認済みの事実)。出力は **JSON スキーマで検証**し、不正時は制限付き再試行 → 失敗は手入力画面へ。
- **事実情報**(価格・採用条件・診療内容)は「承認済みファクト」から引き、期限切れは生成停止。架空の実績・条件を生成しない。
- AI 利用量・原価を顧客別に記録(ADR-0002 のイベント)。使用量上限をアプリ側で強制(予算アラートだけに頼らない)。

### 4.6 日本語タイポグラフィ(品質の要)

- フォント: 商用利用・動画埋め込みが可能なもの(OFL 等)のみ。ライセンスを台帳化。
- 要件: 縦書き、禁則処理、句読点ぶら下げ、書記素単位のタイプライター演出、文字あふれ検査(最小文字サイズ・最大行数)、字幕安全領域。
- **文字あふれはテスト対象**(golden frame テスト: 同じ入力 → 同じ画像)。長文は再生成かユーザー修正を促し、無制限縮小はしない。

### 4.7 音(BGM)

- 初期: 文字+BGM。**商用・SNS 利用が許諾された音源のみ**(自社ライセンス音源 or 明確な商用ライセンス)。市販曲・SNS 内音源は使えない前提。
- ナレーション(TTS)はオプションで後続。使う場合は原価・利用規約・声の権利を確認。

## 6. データモデル(最小)

```
wrapit_tenants/{tenantId}                      会社(契約単位)
  members/{uid}                                role: owner|admin|editor|reviewer|viewer
  brand/current                                version, logo, colors, fonts, tone, prohibited[], defaultCta
  assets/{assetId}                             storagePath, mime, tags[], rights, consent, expiry, active
  facts/{factId}                               text, source, approvedBy, validUntil, status
  templates/{templateId}/versions/{v}          immutable
  projects/{projectId}                         brandVersion, templateVersion, scriptRevision, status
  jobs/{jobId}                                 inputHash, idempotencyKey, status, attempts, progress, outputId, errorCode
  outputs/{outputId}                           storagePath, durationMs, approval: draft|review|approved|rejected
  usage/{eventId}                              renderSeconds, aiTokens, costJpy
  audit/{eventId}
```

- `tenantId` は認証から決定し、クライアント指定を信用しない。全クエリ・署名 URL に tenant 認可。
- ジョブ状態: `queued → running → validating → uploading → succeeded|failed|canceled`。承認は別軸。
- 承認後に内容を変えたら再承認。公開済みの上書き禁止。

## 7. コンプライアンス・安全

- **承認なしで公開しない**(書き出し/下書き連携まで)。
- 医療広告・景表法等の確認欄: 体験談、ビフォーアフター、最上級表現、効果保証、価格表示(§5 のチェッカーで補助。責任者承認が必須)。
- 素材: 許諾済みのみ、人物の同意撤回を反映、患者情報・カルテ・画面映り込みを素材登録させない。EXIF 除去、MIME/容量検証。
- 第三者の動画・音楽・デザインを無断複製しない(「参考リールの再現」ではなく自社デザイン)。
- ログに素材内容・トークンを出さない。SSRF 対策(任意 URL 取得禁止)。

## 8. 価格・原価(仮説。実測後に確定)

- 原価の主要因: レンダー CPU/メモリ秒、AI トークン、ストレージ/転送。**1 本あたり原価を PoC で実測**してから価格を決める。
- 課金単位の仮説: 月間本数(または合計秒数)の**利用枠+追加パック**。無料枠は小さく(透かし or 本数制限)。
- DeckIt とのセット割・BuzzIt からの導線(ADR-0002 のイベントで複数製品契約率を計測)。
- 目標原価・粗利率は実測後に設定(現時点で数値は置かない)。

## 9. フェーズ計画

| Phase | 内容 | 完了条件(受入) |
|-------|------|------------------|
| **R0** PoC(1〜2 週) | 方式比較(§4.3)。独立ディレクトリで 25 秒・縦書き・写真 3 枚・段階表示・CTA・BGM。**本番・既存製品に触れない** | 判定基準 5 項目の実測表。方式とライセンスの結論(ADR-0003) |
| R1 MVP コア | Auth・ブランド・素材・テンプレ 1 種・プレビュー・非同期レンダー・MP4 保存 | 10 本連続成功、文字あふれ検査、二重実行しない、他 tenant 拒否 |
| R2 制作 UX | テンプレ 3 種、AI 台本(JSON 検証)、承認フロー、バッチ | 承認なし書き出し公開ゼロ、失敗ジョブだけ再試行可 |
| R3 連携 | BuzzIt への下書き連携、DeckIt からの文面インポート(任意) | 実 API で確認(モックと区別) |
| R4 商用化 | 課金(Stripe 等)、利用枠、LP、利用規約・プライバシー、監視 | 原価実測に基づく料金、退会・データ削除手順 |

**判断ゲート**: R0 で「原価が料金に見合わない」「日本語品質が出ない」「ライセンス不可」のいずれかなら、方式変更か中止を決める。R1 完了時に**実顧客 3〜5 者のテスト**で需要を確認してから R2 以降に進む。

## 10. リスクと対策

| リスク | 対策 |
|--------|------|
| ライセンス(レンダラー・フォント・音源) | R0 の最初に確認・台帳化。不可なら代替案へ |
| レンダー原価が高い | ブラウザ内レンダー(D)併用、解像度/尺の制限、キャッシュ(固定背景の事前レンダー) |
| 「AIっぽい」品質 | 実素材中心、デザインは人がテンプレ化、AI は台本のみ |
| 開発の分散(製品が多い) | R0 は 1〜2 週で打ち切れる設計。既存製品の安定化(CI・課金テスト)を並行で優先 |
| 法令・SNS 規約変更 | 公開前に Instagram/TikTok の最新要件を確認。自動公開しない |
| 一人運営での負荷 | R1 は最小機能に絞る。サポートはドキュメント+FAQ から |

## 11. 次にやること(R0 の着手項目)

1. ライセンス確認: Remotion(SaaS/商用条件)、候補フォント、BGM 音源。
2. 名称・商標・ドメインの確認(§2)。
3. `wrapit-poc/`(リポジトリ外または未追跡ディレクトリ)で 25 秒動画を A と D で作り、実測表を作成。
4. ADR-0003(レンダリング方式・テンプレ方式)を記述。

> 実装に進む前に、PoC の結果と原価を見て最終判断する。ここまでで本番・既存製品への変更はない。
