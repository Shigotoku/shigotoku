## 1. 目的とゴール

### 1.1 目的

検索（SEO）・生成AI検索（GEO）・地図検索（MEO）からの流入を、**「データで見つけ → 安全に直し → 効果を測る」** 運用として半自動化する。人が毎回「何を直すか」を考えなくてよい状態にする。

### 1.2 ゴール（段階別）

| 段階                  | ゴール                                                                              |
| --------------------- | ----------------------------------------------------------------------------------- |
| Phase 1（メディトク） | 月1回の確認で、改善候補が自動で出る。承認すると修正PRが作られ、効果が追跡できる     |
| Phase 2（とくなが）   | 医療広告ガイドラインを守りつつ、同じ仕組みで地域集患（診療科×地域クエリ）を改善する |
| Phase 3（外販）       | 他クリニック・他社が自分のサイトを接続して使える。データは顧客ごとに完全分離        |

### 1.3 現状ベースライン（2026-10-22 時点）

- Search Console（`sc-domain:meditoku.com`）登録済み。サイトマップ成功・210ページ検出・直近約3か月の総クリック 4,497。
- SEO/GEO基盤は実装・デプロイ済み（メタ・構造化データ・`robots.txt`・`llms.txt`・IndexNow・Bing登録）。
- 計測は GA4 導入済み。ただし**検索データの保存・分析・施策履歴は未整備**（Search Console は直近16か月しか保持しない）。

## 2. 調査結果の採否（要件に反映した判断）

2つの調査は方向が一致しているが、食い違いと注意点がある。**本要件では下記のとおり判断する。**

| 論点                               | 調査A                         | 調査B                                                     | 本要件の判断                                                                                                    |
| ---------------------------------- | ----------------------------- | --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| 「閲覧数（ページビュー）」の取得元 | GSC中心                       | **GSC APIでは取得不可。GA4が必要**                        | **GA4 Data API を必須とする**（閲覧数はGA4、検索表示・順位・CTRはGSC）                                          |
| 反映方式                           | WordPress REST API を最有力   | WordPress第一、差分patch方式                              | **自社サイトは Astro＋Cloudflare Pages（Git管理）のため「Git PR方式」を第1採用。WordPress連携は外販段階で追加** |
| `llms.txt`                         | 自動配置を差別化機能に        | Googleは必須としていない                                  | **維持するが効果の根拠にしない**（AI向けの補助。主軸は通常SEOと引用されやすい構造）                             |
| FAQ構造化データ                    | 自動デプロイを推奨            | **2026-05以降 FAQリッチ表示は廃止。主力にしない**         | **FAQスキーマの量産を機能にしない。** FAQ本文の価値向上を優先                                                   |
| GEOの測り方                        | 引用率の追跡                  | 「GEOスコア」の一点化は避け、言及・引用・流入を別々に測る | **指標を分離して保存**（§6.4）                                                                                  |
| 自動化の範囲                       | 承認付き（Human-in-the-Loop） | 低リスクのみ自動、医療本文は承認必須                      | **一致。リスク分類で自動/承認を分ける**（§5.3）                                                                 |
| 価格・開発費                       | 競合価格を列挙                | 概算あり                                                  | **参考値扱い。未検証のため、外販前に再調査**（§10）                                                             |

> 両調査の外部情報（競合価格・Google仕様）は、本書作成時に一次情報での再検証はしていない。外販判断の前に、API仕様・料金・規約を公式ドキュメントで再確認する。

## 3. スコープ

### 3.1 対象

- **対象サイト**: メディトク（Astro 5 + Cloudflare Pages、`commercial/landing-page`）／とくなが HP（同じ作り方。`wordpress-to-astro-clinic` テンプレート由来を想定）。
- **データ源**: Search Console API、GA4 Data API、サイト自身のクロール、AI検索の定点観測。Phase 2以降で Google Business Profile。

### 3.2 対象外（初期）

- 患者の個人情報・問診・予約内容の取り込み（**取り込まない設計**。§7）
- 記事の大量自動生成・無承認の自動公開
- Google Indexing API の利用（一般ページは対象外の用途）
- `robots` / `noindex` / `canonical` の自動変更（原則禁止）

### 4.2 月次の基本フロー（月1回開けば足りる）

1. 「今月の結論」を開く（増減と、やること上位3件）
2. 改善候補を確認（根拠の数字つき）
3. 修正案の差分を見て承認／却下
4. 承認分が反映され、2〜6週間後に効果が自動で戻ってくる

## 6. データ要件

### 6.1 データモデルの原則（外販を見据えて Phase 1 から適用）

- **テナント（顧客）→ サイト → ページ → クエリ**の階層を最初から持つ。
- すべてのテーブルに `tenant_id` を持たせ、アクセス制御はテナント単位で行う。
- 既存方針に合わせ、**キー構造（PK/SK）や既存フィールドの意味は後から変えない**（`data-compatibility` ルール準拠）。

### 6.2 主なエンティティ

`Tenant` / `Site` / `Page` / `DailySearchMetric`(日×ページ×クエリ×端末) / `DailyAnalyticsMetric` / `CrawlSnapshot` / `Opportunity`(改善候補) / `Change`(変更案・承認・反映) / `ChangeResult`(効果測定) / `AiProbeRun` / `PolicyRule` / `AuditLog`

### 6.3 取得上の制約（設計に織り込む）

- Search Console API: 全行は返らない。1レスポンス最大25,000行、1日あたり約50,000行まで。**日次で取得してページングし、合計値は「一致する」と仮定しない**。
- クエリ件数が少ない行は LLM に渡さない（小集団の保護）。
- GA4 は標準プロパティのクォータに注意（バッチ取得）。

### 6.4 指標の定義（GEOは分離して保存）

- 検索ファネル: 表示 → クリック → ページ閲覧 → 主要CTA → 資料請求/予約
- AIファネル: プロンプト群 → 言及 → 自サイト引用 → 引用順位/論調 → AI経由流入 → CV
- 「GEOスコア」の単一指標化はしない。

## 8. アーキテクチャ方針（案）

```
[Search Console API] [GA4 API] [サイトクロール] [AI検索の定点観測]
            └────────────┬────────────┘
                 日次バッチ（Lambda/EventBridge 等）
                         ↓
              DB（テナント分離・長期保存）
                         ↓
          抽出ルール → 改善候補 → LLM改善案 → 医療広告チェック
                         ↓
              管理画面（承認・Diff・履歴）←Cognito
                         ↓ 承認
              Git PR 作成（GitHub）→ マージ → ローカルwranglerデプロイ
                         ↓
              反映後の効果測定 → 必要ならrevert PR
```

- **配信方式は Git PR 方式（第1）**。JavaScript での後付け書き換えは採らない（解約で消える／AIクローラーに見えないため。調査Aの指摘を採用）。
- WordPress 連携は外販段階で追加（REST API＋アプリケーションパスワード or 専用プラグイン）。
- 既存資産を再利用: 認証（Cognito）、AWS基盤、メディトクのサービス管理（ワークス系の登録/課金）。
- 抽出はまず**ルールと統計**で絞り、LLM は絞った候補にだけ使う（費用と品質のため）。
